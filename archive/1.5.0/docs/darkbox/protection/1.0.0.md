# Darkbox protection extension 1.0.0

This normative extension belongs to namespace `studio.illegal.darkbox.protection` and supports Darkbox 1.1.0. Its extension version, block version, common version and application format version are independent. Implementations explicitly register supported versions. The terms MUST, MUST NOT and MAY express conformance requirements.

## Descriptor

The manifest member `extensions["studio.illegal.darkbox.protection"]` MUST match the adjacent [JSON Schema](1.0.0.schema.json). It has `version: "1.0.0"`, `required: true` and `data` with:

| Field | Meaning |
| --- | --- |
| `packageId` | 128-bit package identity, exactly 32 lowercase hexadecimal characters |
| `signature` | `algorithm: "Ed25519"`, public `signerId`, and fixed `path: "extensions/studio.illegal.darkbox.protection/manifest.ed25519"` |
| `inventory` | Complete sorted array of `{path, size, sha256}` file records |
| `files` | Array of `{path, keyId}` declarations for individually encrypted resources |
| `sqlite` | Array of `{database, table, column, recordIdColumn, keyId}` declarations for protected SQLite columns |

`packageId` MUST be generated from 128 uniformly random bits when creating a distinct package identity. Saving revisions retains it. A copied project can retain its identity only if it represents the same project; assigning a new identity requires re-encryption of every protected block. It is public and is not a secret key. Identifiers select application-managed keys. `keyId` and `signerId` are case-sensitive ASCII strings, 1 to 255 bytes using letters, digits, `.`, `_`, `-`. Different identifiers MUST NOT disguise nonce reuse under the same actual key.

All paths follow the common path rules, with exact case and no decoding or normalization. File declarations are unique. Protected columns are unique by the exact `(database, table, column)` tuple. SQLite names are exact UTF-8, 1 to 255 bytes, without NUL. Generic JSON Schema character bounds do not replace these byte bounds. The signature namespace folders appear in `folders`. No descriptor member contains a key, password or license credential. Protection MUST be required because base-data edits require a new inventory and signature.

## Public and protected contents

Manifest, root README, canonical documentation, signature, application-profile document and information needed to recognize protection MUST remain readable. Declared database files MUST remain ordinary SQLite. The extension MUST NOT declare any of these as encrypted files. Other individual regular resources, including extension resources, MAY be encrypted. Each encrypted file consists of exactly one block described below, including the header and tag.

The application profile MUST document protected columns, their exact plaintext encodings and structures, NULL behavior, stable identifiers, public fields and attachment relationships. A block can contain one value or structured values. All non-NULL values of a declared protected column MUST have SQLite storage class BLOB and contain exactly one block. SQL NULL denotes absence, not encrypted empty plaintext. Each protected table MUST be an ordinary application table, not a view, virtual table or shadow table. Protected and identifier columns MUST be stored columns, not generated or hidden columns. The identifier column MUST differ from all protected columns in that table. Its values, including rows with NULL protected values, MUST be unique nonempty UTF-8 SQLite TEXT without NUL, at most 1024 bytes. Equality and authentication use exact UTF-8 bytes, independent of SQL collations. Composite identifiers must be encoded into one stable TEXT column by the profile. Identifiers are immutable while ciphertext is retained.

The producer MUST encrypt sensitive bytes before inserting them into SQLite. It MUST NOT insert plaintext and encrypt it later. Updating a formerly plaintext database in place cannot establish that old values are absent from pages, freelists, WAL, rollback journals, backups or caches. Producers converting existing plaintext data MUST create a fresh database containing only the intended public values and encrypted BLOBs, and manage old copies according to application policy. SQLite integrity checks cannot prove that plaintext never existed. Sensitive plaintext is not written into packaging staging files by the verifier.

## Binary block format

Blocks use AES-256-GCM, a 32-byte key, 12-byte nonce and 16-byte authentication tag. Integers are unsigned and big-endian. No padding, base64, JSON wrapper or trailing bytes are permitted inside the binary block. The ciphertext length equals plaintext length and MUST be at most `2^36 - 32` bytes. Reader policies may impose smaller limits.

| Offset | Bytes | Meaning |
| --- | --- | --- |
| 0 | 4 | ASCII `DBXP` (`44 42 58 50`) |
| 4 | 1 | Block version `01` |
| 5 | 1 | Algorithm `01`, AES-256-GCM |
| 6 | 2 | Reserved, both zero |
| 8 | 12 | Nonce |
| 20 | 8 | Ciphertext length N |
| 28 | N | Ciphertext |
| 28 + N | 16 | Authentication tag |

Total length is `44 + N`. Empty plaintext is permitted. Invalid magic, reserved bytes or length are malformed data; unimplemented block version or algorithm is unsupported. Never return unauthenticated plaintext after failure.

For every new encryption operation under a given actual key the nonce MUST be distinct, across files, columns, packages, devices and saves, including aborted saves. Nonce allocation MUST survive crashes and coordinate all writers sharing a key. A persisted counter with a uniquely allocated device prefix is suitable; see [RFC 5116 sections 3.1 and 3.2](https://www.rfc-editor.org/rfc/rfc5116.html#section-3.1). Random selection alone does not guarantee distinct nonces. Exhaustion or inability to reserve a unique nonce requires refusing encryption or rotating to a fresh key. Retaining an identical block in its identical context is not a new encryption. Readers reject duplicate observed nonces per key identifier, and per actual key when keys are available. Readers cannot prove historical nonce uniqueness or discover key aliases without keys.

## Additional authenticated data

Define `LP(s) = U32BE(length(UTF8(s))) || UTF8(s)`, where length counts bytes, and `||` means byte concatenation. No terminators, Unicode normalization, whitespace rewriting, path case folding or URL decoding are applied to strings. The domain prefix is the 22 ASCII bytes of `Darkbox-PROTECTION-AAD` followed by one zero byte, 23 bytes total. Implementations MUST use the literal byte string `44 61 72 6b 62 6f 78 2d 50 52 4f 54 45 43 54 49 4f 4e 2d 41 41 44 00`.

The AAD is:

```text
prefix || block[0..28] || LP("studio.illegal.darkbox.protection") ||
LP("1.0.0") || LP(packageId) || LP(keyId) || context
```

For a file, `context = 01 || LP(path)`. For a SQLite BLOB, `context = 02 || LP(databasePath) || LP(table) || LP(column) || LP(recordId)`. The tag authenticates the header, key selection and location. Including the database path also prevents substitution between databases with identical schemas. Fields come from the signed declarations and actual row identifier, never from an untrusted header location. A changed path, package identity, key identifier, table, column or record identifier requires decrypting and encrypting again with a fresh nonce.

This profile instantiates the AEAD interface in [RFC 5116](https://www.rfc-editor.org/rfc/rfc5116.html), using AES-256-GCM from section 5.2. Payload types and structures are defined by the application profile, not by this extension.

## Complete inventory and detached signature

`inventory` MUST list every regular ZIP file exactly once, except precisely `manifest.json` and the declared fixed detached signature path. No other exclusion is permitted. Directory entries are excluded; common folder inventory checks still apply. Records MUST be sorted by exact ASCII path bytes, strictly increasing. `size` counts uncompressed bytes and is a nonnegative integer at most `9007199254740991`. `sha256` is 64 lowercase hexadecimal characters, computed over the exact uncompressed entry bytes. For encrypted files those bytes are the complete ciphertext block. Database hashes cover the complete SQLite file, including public values and protected BLOBs. Documentation, the canonical bundle catalog, application profile and all extension resources are included.

Missing, additional, duplicate, size-different or hash-different files fail inventory verification even when ZIP CRCs are valid. Every ZIP entry retains the common CRC requirements. The canonical bundle additionally remains checked against locally trusted official bytes; a valid package signature cannot authorize altered canonical documentation.

The detached file contains exactly 64 raw Ed25519 signature bytes. Use pure Ed25519 from [RFC 8032](https://www.rfc-editor.org/rfc/rfc8032.html), with an empty external context and no prehash variant. Sign the exact uncompressed bytes of `manifest.json`, including whitespace and line endings. No JSON canonicalization or digest substitution is performed. The signed manifest declares algorithm, signer identifier and signature path before signing. Reject malformed signatures, noncanonical scalar encodings and small-order signing or R points. Library implementations use strict verification. The signature does not authenticate ZIP compression, ordering or timestamps.

Save order: prepare encrypted payload and public metadata; build the complete inventory; serialize final manifest; sign those exact bytes; write the detached signature; validate the complete candidate; publish atomically. Never modify the manifest after signing. The two inventory exclusions avoid circular hashes while the signature authenticates the inventory and all protection declarations. Signature bytes are structurally and cryptographically verified separately.

## Application key ownership and trust

Applications supply a decryption-key provider and a mapping of trusted signer identifiers to public Ed25519 keys. They control key selection, authorization, license/password policy, key distribution and revocation. Keys MUST NOT be embedded in the package or reports. Packaged public keys or certificates do not establish trust and are never imported automatically. A trusted signature authenticates the issuer under application policy; it does not certify application semantics, prevent replay or establish that the contents are safe to execute. Revision freshness and anti-rollback policy belong to the application.

An application expecting protected projects MUST require this extension by external policy. Otherwise removal of the entire descriptor together with its namespace resources is indistinguishable from an intentionally unprotected archive. Applications MUST NOT infer protection solely from filenames or allow a protected project to become writable without the externally required checks.

## Verification and opening

Without decryption keys, readers can verify the signature using trusted public keys, the full ciphertext inventory, block headers, public metadata, canonical documentation and standard SQLite integrity and foreign-key checks. They MUST explicitly report every encrypted block whose AEAD authentication and plaintext interpretation were not checked. Key absence is a locked content state, not corruption. With a key, readers additionally authenticate each block against its constructed AAD. Wrong keys and changed ciphertext or context produce an authentication failure; the verifier cannot infer which caused it. Plaintext meaning, type validation and profile invariants remain application responsibilities in both cases.

| Condition | Result |
| --- | --- |
| Decryption key absent | Public/locked view permitted after required public verification; content authentication unchecked |
| Signer unknown | Trust unsupported; ordinary opening and saving refused; diagnostic inspection permitted |
| Common, extension, block version or algorithm unimplemented | Unsupported capability; ordinary opening and saving refused |
| Detached signature missing/malformed/invalid | Invalid package; ordinary opening and saving refused |
| Inventory mismatch | Invalid package; ordinary opening and saving refused |
| AEAD authentication failure | Invalid protected content; ordinary opening and saving refused |
| Unknown required extension | Unsupported; ordinary opening and saving refused; diagnostic inventory permitted |

Diagnostic inspection never certifies required protection and never authorizes saving. Generic reports MUST keep application-profile validation separate. A verifier may continue independent public checks after trust failures, but MUST NOT label the package authenticated.

## Extension API and safe saving

Libraries expose explicit registration of namespace/version verifiers and application-owned key/trust providers. A required unknown verifier or unsupported version blocks ordinary opening and saving. Recognizing a verifier does not imply writer support. Verifiers without writer capability MUST refuse saves requiring their synchronization. Unknown optional descriptors and resources remain preserved under the common rules.

Every modification MUST retain required protection, regenerate the complete inventory and create a valid new signature. If signing, extension-writing or necessary encryption capabilities are absent, save MUST fail before replacing the original. Unchanged encrypted blocks may be preserved without decryption keys only when all their authenticated context and bytes stay unchanged. New/modified/moved blocks require authentication with the appropriate key, and new encryption requires a fresh reserved nonce. Deleting encrypted content can be a legitimate application edit; declarations and application invariants remain consistent.

The Rust writer preserves package identity and file/column protection declarations and verifies retained blocks by both bytes and context. It supports public edits and already encrypted updates, validates a separate candidate and refuses unsupported context migration. Applications performing a broader migration build a new candidate with re-encrypted blocks, retain the source and verify it before adopting it. Callers coordinate exclusive access during save; source hashes detect changes observed during processing. A failure preserves the source and existing destination. Published canonical bundles are always immutable.

## Interoperability

The adjacent [vectors](1.0.0.vectors.json) contain complete keys intended only for testing, nonces, plaintext, AAD and block bytes for file, empty file and structured SQLite values, plus exact manifest bytes and an Ed25519 signature. They were produced independently with Python cryptography/OpenSSL and checked by RustCrypto. The generator is `scripts/protection_vectors.py`. Test keys MUST NOT be used for real data. Use separate unique nonces even in fixtures.
