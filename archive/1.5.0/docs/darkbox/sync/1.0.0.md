# Darkbox synchronization extension 1.0.0

This normative extension belongs to `studio.illegal.darkbox.sync` and common Darkbox 1.5.0. MUST, MUST NOT and MAY express conformance requirements.

## 1. Scope and release identity

The official namespace is studio.illegal.darkbox.sync, extension version 1.0.0, for common specification 1.5.0. Existing common 1.4.0 artifacts remain byte-for-byte immutable. A package carrying synchronization state MUST declare this extension required. Existing ZIP exports, directory locks, HotCapture and exact-base deltas retain their meanings.

There is no required protocol-specific executable, server, backup product, CRDT runtime or service account. Implementations use SQLite, strict JSON and SHA-256; no protocol-specific external service is required. The protocol specifies a portable representation of causal registers, observed-remove sets and tombstoned sequence nodes. Independent implementations MUST follow the wire rules and logical state definitions below.

Each machine owns a local live library and local durable outgoing queue. A cloud client copies an exchange directory. SQLite databases, WAL files, OS locks, private staging directories and writable local journals MUST NOT be shared as the replication mechanism.

Version 1 supports concurrent offline editing, complete local resource availability, deterministic logical convergence, retained conflicting alternatives, immutable exchange segments, complete bootstrap snapshots, crash-safe queues and explicit repair diagnostics. It deliberately has no automatic history/resource deletion, distributed format migration, online membership consensus, arbitrary SQL replication, character-level collaborative text editing or encrypted sync mode.

Security mode is explicitly trusted-folder-plaintext. The operator trusts all writers with write access to this domain and the selected cloud account/provider with plaintext. Hashes establish byte integrity and identity, not author authentication. Protected Darkbox libraries MUST be refused by v1 sync attachment. Existing protection metadata MUST NOT be stripped or downgraded to make attachment work. Signing/encryption and authenticated enrollment require a separately specified protocol mode/version; they are not silently inferred from existing protected snapshots.

## 2. Guarantees and assumptions

For a fork-free domain, supported fixed profile and operations within reader limits, two conforming peers that durably receive the same causally closed transactions and referenced object bytes compute the same canonical logical state, conflicts and synchronized application projection. Physical SQLite pages, ZIP compression and local-only fields need not match.

A valid local transaction remains queued until its exact bytes can be published. A received transaction is applied at most once. A transaction is never partly visible. Neither delivery order, filesystem modification time nor the wall clock chooses application meaning.

Eventual progress assumes the transport eventually exposes intact published files and preserves them, peers retry scanning, all required objects/dependencies remain obtainable, and the application eventually runs. A missing object, lost file, unsupported operation, full disk or paused cloud client can prevent progress. The folder API cannot certify that the provider uploaded a locally published file or that an unknown/offline device received it.

A convergent visible value does not mean every edit is simultaneously visible. Concurrent alternatives remain queryable, superseded writes remain recoverable in retained history, and delete-hidden data remains recoverable through explicit restore. External destruction of all copies is outside this guarantee.

## 3. Domain, profile and incarnation identity

The domain creator generates independent 128-bit random lowercase-hex syncId and packageId values, retaining an existing packageId when attaching the same logical library. They are not secrets. Copying a local library does not authorize creating a second initial import into the same domain.

The immutable library.json root contains these exact members:

- kind = darkbox-sync-domain.
- protocolVersion = 1.0.0.
- syncId and packageId.
- commonVersion = 1.5.0.
- application: profile identifier and exact formatVersion.
- profile: path profile/profile.md, decimal-string size, lowercase sha256.
- mapping: path profile/mapping.json, decimal-string size, lowercase sha256.
- encoding = jcs-strings-v1.
- merge = causal-records-v1.
- security = trusted-folder-plaintext.

The hash of the exact canonical library.json bytes is rootSha256. All other protocol records include syncId and rootSha256. The human-readable profile, mapping and root bytes are immutable for the domain. Joining pins the selected root hash in local configuration after checking the package identity, profile and supported capabilities. A different root for the same syncId is a domain conflict, never an update.

A persistent deviceId and label identify an installation for display only. They do not allocate operation identity. Every writable SyncSession opening generates a fresh uniformly random 128-bit replicaId, called an incarnation, and registers an immutable replica descriptor with the domain hash, replicaId, deviceId and label. One local exclusive guard owns a session.

A reopened, restored or copied installation always starts a new incarnation, even if its earlier database contains counters. It can republish already committed/sealed bytes from older incarnations, but MUST NOT append a new transaction to an old incarnation. Prepared transaction bytes are sealed in the local SQLite commit, not reconstructed after restart. This prevents normal backup restores from reusing a persisted stream counter. Copying or checkpointing a running process with its active identity is not supported; divergent reuse is a detectable fork.

This costs one frontier entry per writing session. The first version keeps that metadata indefinitely. Implementations report size-policy exhaustion before allowing an edit they cannot encode; long-lived-domain compaction requires explicit rebootstrap into a new domain.

## 4. Exchange layout and publication

The user selects one domain directory:
    library.json
    profile/profile.md
    profile/mapping.json
    replicas/<replicaId>/replica-<length16>-<sha256>.json
    replicas/<replicaId>/segments/<first20>-<last20>-<length16>-<sha256>.json
    replicas/<replicaId>/snapshots/<length16>-<sha256>.json
    replicas/<replicaId>/snapshots/<sha256>.darkbox
    replicas/<replicaId>/receipts/<serial20>-<length16>-<sha256>.json
    objects/<first-two-hash-characters>/<sha256>-<length16>.blob

Numbers in filenames are zero-padded lowercase hexadecimal for length16 and decimal for first20, last20 and serial20. Transaction sequence starts at 1 and is unsigned 64-bit; decimal names compare as fixed-width ASCII. Protocol record counters use the decimal-string encoding below, not padded forms.

Replica descriptors, segments, snapshot descriptors, snapshot packages and receipts each have exactly one incarnation writer. Objects have a deliberate exception: several writers MAY publish the exact same bytes at the same content-addressed path. No writer can replace existing different bytes. This is the only shared-writer namespace. The hash and length bind the complete object, and concurrent identical publication does not create different logical values. A transport may nevertheless leave redundant identical conflict-copy files.

Writers build a complete private candidate, flush it and publish by atomic no-clobber creation/rename on the local filesystem. The final file is never reopened for writing. Durability includes the containing directory where supported. If a final path already exists, verify its complete bytes; exact identity is a successful retry, any difference is an error. New ZIP publication keeps the current no-persistent-sidecar behavior. No cloud directory advisory lock is a distributed lock.

Local rename does not imply atomic remote exposure. A scanner always verifies length, hash and content after reading through a handle and protecting against a changed file. A short, changed or hash-mismatching transport candidate remains pending_bytes and is never applied. An unchanged bad candidate can produce a persistent attention diagnostic, but elapsed time alone does not establish corruption. If bytes match their advertised digest but violate the protocol, report invalid_record. A renamed or missing published file is a repair need, not permission to skip it.

Only exact lowercase ASCII canonical paths are authoritative. Unknown files are ignored for application with bounded diagnostics. Case aliases and noncanonical conflict names are never selected by directory enumeration order. When a bounded diagnostic read of a noncanonical JSON candidate identifies a completely valid segment for this root, compare its transactions with known logical identities: identical bytes are duplicate evidence; a different hash for the same replica/sequence is fork evidence. Do not apply that candidate directly. An operator/repair helper may republish verified exact bytes at the canonical path without overwriting anything. Unparsed/over-limit ignored files remain explicitly unchecked, so a scan never claims absence of forks in arbitrary ignored bytes.

No required mutable head/index file exists. Optional local caches and filesystem notifications are hints; periodic bounded scans are authoritative.

## 5. Exact encoding and value grammar

All protocol JSON files are canonical RFC 8785 JSON, UTF-8, without BOM, final newline or trailing bytes. Duplicate keys, invalid Unicode and noncanonical encodings are rejected after complete length/hash validation. Object keys are fixed ASCII protocol keys. User map keys are stored as strings in entry arrays, not as protocol property names. No Unicode normalization or case folding is applied.

No JSON numeric token occurs anywhere in protocol records. Counters, sizes, indices and clock values are canonical decimal strings: zero is 0; positive values have no leading zero; unsigned fields have no sign and are bounded by 2^64 - 1. An operation index is zero-based and at most 4095. This avoids host floating-point rounding and does not enable arbitrary_precision features in consumers.

Typed values are:
- {type: null}: a present null value, distinct from an absent register.
- {type: bool, value: true or false}.
- {type: text, value: Unicode string}.
- {type: integer, value: canonical signed decimal string}; no plus sign or negative zero, at most 4096 digits.
- {type: decimal, coefficient: canonical signed integer string, exponent: canonical signed integer string}; value is coefficient times 10^exponent. Nonzero coefficients have no trailing zero, zero is coefficient 0/exponent 0; coefficient at most 4096 digits, absolute exponent at most 4096.
- {type: list, values: ordered array of typed values}.
- {type: map, entries: array of {key, value}}, unique keys sorted by exact UTF-8 bytes.
- {type: record, collection, id}: a reference, with the target create event in causal context.
- {type: blob, sha256, size}: exact immutable bytes; size is unsigned decimal.

A register can hold any typed value atomically. A list/map register is replaced as a whole; nested edits are not automatically merged. An OR-set uses typed values with equality defined by their canonical bytes. These typed values express data, never commands, SQL or loadable code. Field and collection identifiers are case-sensitive ASCII [A-Za-z][A-Za-z0-9_]{0,63}; database/table/column names remain values in the mapping and follow profile rules.

A cleared register has no value and is represented by a distinct assign operation with present:false; present:true requires a typed value. Clearing participates in conflict handling like any assignment.

Default protocol bounds: at most 1,048,576 bytes per canonical transaction, 4096 operations per transaction, 4,194,304 bytes and 256 complete transactions per segment, and typed-value depth at most 64. Oversized text/structured values must be external blobs interpreted by the profile. Reader policies may impose lower operational limits and return unsupported_limits, never silently truncate. Resource files/snapshot packages use streaming limits, not the small JSON-segment bound.

## 6. Transactions, dependency frontiers and hashes

A transaction has exactly kind, protocolVersion, syncId, rootSha256, replicaId, sequence, previous, dependencies, lamport and operations. kind is darkbox-sync-transaction, protocolVersion is 1.0.0.

previous is null for sequence 1, otherwise the SHA-256 of the previous canonical transaction in the same incarnation. dependencies is the complete author-applied frontier before this transaction: a unique array sorted by replicaId, each {replicaId, sequence, sha256}. Zero entries are omitted. A dependency tip commits to that replica's chain through previous hashes.

For sequence s greater than 1, dependencies contains the author's own exact sequence s-1 and previous hash. Sequence 1 omits itself. A dependency frontier MUST be causally closed: every covered tip's own dependencies is also covered at an equal or greater sequence on the same verified chain. A reader verifies all intermediate transactions, or the same exact history from a complete bootstrap snapshot. It cannot accept an unaudited numeric counter as proof of coverage.

Define lamport = 1 + maximum lamport among dependency tips, with maximum of the empty set equal to 0. Check this exact equality after dependencies are known. Wall-clock timestamps have no protocol meaning. Overflow refuses a new write, never wraps. This supplies causal-compatible deterministic tie-breaking without a clock-skew rule; the dependency vectors, not Lamport values, detect concurrency.

A transaction ID is (replicaId, sequence); txSha256 hashes its exact canonical bytes. An operation dot is (replicaId, sequence, index), represented as replicaId:sequence:index with canonical decimal components. Operations in one transaction are ordered by index.

An event x is observed by operation y if x's transaction is covered by y's dependency frontier, or both are in the same transaction and x.index is less than y.index. All operation references MUST be observed, not merely already received at the evaluating peer. Validation therefore depends on the author's causal state, not delivery order.

A segment has kind darkbox-sync-segment, protocolVersion, syncId, rootSha256, replicaId, first, last and transactions. It contains complete canonical transaction objects for a contiguous nonempty interval, with matching author identity and last-first+1 count. Group boundaries do not affect semantics. Overlapping segments with byte-identical transaction hashes are harmless retries; an overlapping logical ID with different canonical bytes is a fork. Segment byte length/hash are in the filename, so there is no separately racing integrity sidecar.

Transactions are immutable once committed locally. A publisher may repackage the same sealed transaction bytes into a different valid segment after a crash, but may not regenerate operations, dependencies or transaction hashes. Object publication is attempted first for latency; receivers remain correct if the cloud delivers the segment first.

## 7. Receiver and error state machine

For each scan:
1. Verify the pinned root/profile/mapping and classify complete descriptors, segments and objects. Keep partial files pending.
2. Expand valid segments into transactions keyed by (replicaId, sequence, txSha256). Stage complete bytes durably; duplicates do not cause a second application.
3. Resolve the preceding sequence and exact dependency-tip hashes. A gap blocks that incarnation and causal descendants, not unrelated ready incarnations.
4. Require every referenced blob to be verified and durably installed in the local immutable resource store. Metadata may be inspected while waiting, but the applied frontier cannot advance past that transaction.
5. Validate the entire transaction's encoding, profile types, author-context references, operation preconditions and declared version. Stage projected conflicts rather than rejecting a valid concurrent business conflict.
6. Apply the whole transaction and advance the frontier in one local durable commit. Run to a fixed point until no ready transaction remains.

No global sort of all received transactions is required. Any causally valid application order produces the same canonical state. A deterministic scheduler may prefer smaller (lamport, replicaId, sequence), but merge correctness cannot rely on that scheduling choice.

Statuses are separate dimensions: local_commit, queued, published_locally, received_by_known_peer, pending_bytes, pending_dependency, pending_object, unsupported, invalid_record, forked, projection_conflict, and io_error. A UI may display them more simply, but it must not collapse published_locally into uploaded/all-devices-synchronized.

A fully verified different transaction at an already known logical ID is a hard fork. Stop new writes and authoritative application for the affected domain, preserve the current library, all pending/outgoing bytes and both branches, and offer diagnostic export/recovery into a new domain. Never choose a branch by filename/time or silently undo user edits. Previously displayed state is then marked uncertified. The convergence guarantee excludes forked histories; clones/restarts are prevented through new incarnations rather than automatic fork arbitration.

Malformed or unknown-version transactions block their chain and descendants. Unrelated supported transactions may continue unless the root/profile capability itself is unsupported. Report the precise boundary. A conforming sender does not generate invalid records, so this is a diagnostic/recovery state rather than a merge rule.

## 8. Local durability and application boundary

Preferred integration uses a single authoritative SQLite database per sync domain. In one SQLite transaction the application commits:
- application rows or the deterministic projection of the new CRDT state;
- CRDT metadata and canonical accepted history;
- the exact sealed outgoing transaction bytes, identity/counter and hash;
- the new applied frontier and outbox records.

An incoming transaction similarly commits its history, CRDT state, projection/conflict records and frontier atomically. Application-controlled writes to synchronized data MUST use this path. Scanning tables after ordinary unrelated commits is not a reliable substitute.

Tables are documented in the application's profile and stored in the same main database as authoritative synchronized rows, or the sync journal is authoritative and other databases are explicitly rebuildable caches. Do not promise atomicity for an application database and a separate WAL-mode outbox database through ATTACH: SQLite does not provide cross-file atomic commit for that combination.

For resources: write/flush/hash an immutable private local object first, publish it into the local object store without clobbering, then commit its reference and outgoing operation. A pre-commit crash can leave a local orphan; a post-commit crash leaves a referenced complete local object available for retry. The first version does not delete such durable objects automatically. Local-only uncommitted staging files can be cleaned up when no committed transaction references them; deleting published domain objects is a separate forbidden v1 action. No database transaction performs a cloud wait.

The durable journal is the source of truth for preparing segments and reconstructing protocol state. Recovery replays only exact committed bytes, starts a new incarnation, retries publication and resumes pending input. A durable state loss/restore can discard edits made after that backup if every other copy was lost; the protocol cannot invent those bytes.

Multi-database live packages remain legal Darkbox packages, but a profile must choose one synchronized authoritative store or the documented journal/cache model. The SDK must refuse a falsely atomic multi-database adapter.

## 9. Record lifecycle and scalar conflicts

create(collection) creates a globally unique record whose ID is the create operation dot. An SDK can return that ID to later operations in the same transaction. A profile may retain an existing application UUID as a mapped value, but operation identity is never allocated by a colliding database integer key.

assign(record, field, present, value) applies to a record created in the author's causal context. For each field retain all assignments that are causally maximal among assignments to that same field. A new assignment removes only assignments it observes; concurrent assignments remain alternatives. Clearing is an assignment as specified above.

The default displayed candidate is the maximum tuple (lamport, replicaId ASCII bytes, sequence numeric, index numeric) among surviving candidates. Also expose every surviving candidate and dot. Distinct concurrent values set a field conflict; identical alternatives need not alarm the user but retain their identity. A subsequent assignment made after observing all alternatives resolves them. Editing an old offline value without seeing another peer cannot resolve that unseen peer's assignment.

All nonmaximal/superseded writes remain in history in v1. A profile/UI may retrieve earlier values; deterministic display is not permission to erase alternatives.

delete(record) places a permanent tombstone on that record ID. Deletion wins over any concurrent or delayed edit. Existing data, outgoing history and ordering anchors are retained. A causally later edit to a known deleted ID is invalid; an edit concurrent with a deletion is valid history but hidden in the live projection.

There is no implicit resurrection of the same ID. Restore explicitly creates a new record and copies selected fields/resources, optionally recording a provenance reference to the old ID. This handles deletion consistently even when an old PC returns after months. Repeated deletion is harmless. A tombstone is never removed in v1.

## 10. Set fields

set_add(record, field, value) creates an add tag equal to its operation dot. set_remove(record, field, value, tags) names every currently active add tag for that exact typed value visible in the author's causal state. Tags are sorted, unique, belong to the same record/field/value and MUST be observed. A remove of an absent value has an empty tag list and is a valid no-op.

Retain all adds and the union of removed tags. A value is present iff at least one matching add tag is not removed. Consequently, a remove cannot cancel an unseen concurrent add; after observing that add, a new remove can cancel it. Visible values are unique and sorted by canonical typed-value bytes for hashing, though UI presentation may differ.

Deleting the owning record hides its sets without erasing their history. Sets do not imply ordering. Removing a record reference from a set does not delete the target record.

## 11. Ordered collections and concurrent moves

Use an explicitly specified immutable-anchor sequence, with RGA-style tombstones, plus a causal placement register per (record, position field). 

place(record, field, sequence, owner, after) creates a new immutable position node identified by its dot. A sequence is scoped by the position field and the exact (declared sequence name, owner record ID or null) pair. Anchors MUST use the same position field. after is null for that sequence's root sentinel, otherwise an observed existing node in exactly that sequence. Owner and record creates are observed and live in the author's context. The profile declares valid owner/record collection types.

The node stores its record, field, sequence/owner, parent anchor and priority tuple (lamport, replicaId, sequence number, operation index). It also assigns that node ID to the record's placement register using the same multi-value semantics as scalar fields. unplace assigns an absent placement without deleting old nodes.

For each sequence, form the tree of all immutable nodes attached to the root sentinel. Traverse depth-first pre-order; children of one anchor are sorted by descending priority tuple. Always traverse inactive/deleted nodes and their children. Emit a record only if it is live and the node is the default-selected candidate of that record's position register for that field. A competing move survives as a placement conflict even though only one position is displayed.

A parent node must be observed before the new node is created, so parent priority is strictly earlier and cycles cannot form in a conforming history. Old nodes never change parent. A move therefore cannot create a mutable predecessor cycle, and each record/field is emitted at most once. Iterative traversal must tolerate long histories without recursive stack overflow.

Moving a record moves that record, not descendants previously anchored to its former occurrence; those descendants keep their anchor. Concurrent insertions at one anchor use the fixed priority. A move across containers assigns one placement value containing the new owner, so profiles should derive that parent/container column from the same value instead of merging an independent parent register.

This guarantees deterministic order and retained move conflicts, not simultaneous satisfaction of contradictory human reorder intentions. A whole-collection reorder may be a single bounded transaction with several place operations. Profiles must document how records without a selected placement are represented.

## 12. Profile mapping and application invariants

mapping.json is immutable canonical JSON, identifying its mapping version and exact application profile/format version. It enumerates collections, storage identity columns, scalar/set/position fields and types, object references, local-only columns and the single authoritative database or journal/cache contract. Every synchronized operation must reference a declared collection/field with an accepted type.

Application data outside that mapping is local-only. It must never be treated as replicated because the database file happens to contain it. Rebuilding a projection must preserve local-only values keyed by stable identity; initializing a new PC uses profile-declared defaults for those values.

The generic core produces logical records and conflict metadata. The registered profile provides a versioned deterministic projection and full offline human-readable interpretation. Projection is a pure function of canonical logical state and the pinned profile, not of delivery order, current time, local row IDs, locale, network state or random numbers.

The v1 baseline for invalid references, cross-container constraints or uniqueness collisions is quarantine of affected projected records in a documented conflict view, retaining all logical data. Optional profile fallbacks are deterministic derived presentation, not new outgoing user operations. A required missing/deleted reference cannot be silently replaced with an arbitrary local default. Profiles may define a fixed documented fallback entity and behavior if it too is deleted.

A valid causal transaction that causes a concurrent business conflict is accepted into the core and frontier; it must not block all synchronization because a raw SQL uniqueness/foreign-key constraint rejects its naive materialization. Project only valid rows and store the conflicting records in the conflict view in the same commit. Infrastructure failures roll back the whole commit and retry. A missing compatible profile adapter blocks ordinary application, with common transport diagnostics still available.

No archive-provided SQL, JavaScript, WASM or other executable projection is run by the generic verifier. A mapping/schema cannot prove arbitrary application invariants. Reports distinguish transport integrity, core convergence-state verification and application projection verification.

## 13. Snapshots, bootstrap and export

A snapshot is a closed conformant Darkbox package with the required sync extension. Its extension namespace contains:
- the exact domain root and pinned mapping bytes;
- history.jsonl with every canonical transaction covered by its frontier, each followed by one LF, ordered by (replicaId, sequence);
- state.json with deterministic canonical CRDT state, including tombstones, current alternatives, OR-set tags/removals, every position node and selected/conflicting placements;
- checkpoint.json with the exact frontier tips, history size/hash, state size/hash and an objects array mapping every retained (sha256, size) to one unique package path. Object rows are sorted by hash then numeric size, and every referenced blob must have exactly one verified row. A current application resource may supply those bytes; otherwise retain them under the extension's history object store.

The package also has the common canonical bundle, included application-profile document, materialized application database and resources. Declared common resource inventory and optional ZIP compression remain separate from protocol state equality.

The sealed extension descriptor has version 1.0.0, required true, and data containing mode=sealed, syncId, rootSha256, rootPath, mappingPath and checkpointPath, all fixed under extensions/studio.illegal.darkbox.sync/. Paths and all referenced files are validated. The checkpoint carries the immutable profile/mapping bindings and does not include its own hash. The external snapshot descriptor binds the complete .darkbox bytes by length/hash and its checkpoint frontier/state hash. There is no circular hash: package first, external descriptor last.

A working library instead declares mode=working, syncId, rootSha256, rootPath, mappingPath, journalDatabase and journalSchemaVersion=1.0.0. journalDatabase identifies a declared ordinary SQLite database and documented reserved sync tables; the journal is authoritative. Local cloud paths, active private session identity, filesystem paths and keys do not belong in portable manifest metadata.

The v1 complete snapshot includes history, rather than treating a counter vector as sufficient CRDT state. Verify unique contiguous chains through every frontier, all dependency closure and every covered transaction, rebuild core state, compare state.json exactly, then validate the registered profile projection. A generic tool without the adapter reports that application materialization is unchecked. A hash alone cannot prove that a snapshot's database matches its history.

Snapshots MUST retain every resource referenced anywhere in their retained history, including removed values, deleted records and unresolved alternatives, so a third machine can independently replay and recover them. The profile mapping lists this history-resource store as well as currently visible attachments. state.json is an acceleration/cache representation; history supplies an independently rebuildable v1 interpretation.

For capture, freeze a causally closed journal frontier and retain all corresponding immutable resources. Capture database/projection and journal at that same frontier using an application barrier consistent with HotCapture. A generic series of separate SQLite backups is not proof of cross-database coherence. A journal/cache adapter may instead rebuild a private snapshot projection from frozen history.

A new PC selects a completely verified snapshot by causal coverage, not mtime. Prefer a frontier that dominates other verified candidates; among incomparable maxima choose greatest sum of sequence counts, then lexicographically smallest complete-package hash. Replay other uncovered received history afterward. There is no globally latest certificate. Identical logical state can have different ZIP/SQLite bytes.

An existing PC never replaces its state with a snapshot while discarding local operations outside the snapshot frontier. Take the verified union of local committed history and snapshot history, detect forks, then replay unapplied operations and preserve the local outbox/local-only data. A stale snapshot is a safe baseline, not authority to rewind history.

Initial attachment imports one authoritative existing local library into create/assign/set/place transactions, preserving application identifiers through the profile mapping. Publish a complete initial snapshot before offering the domain as ready for another PC. Concurrent independent imports into one domain are unsupported; joining an existing domain bootstraps its history instead.

A full sync backup preserves the extension and complete history. A user-requested portable export of only the visible project must build a fresh ordinary package with the profile-defined materialized state and omit sync internals deliberately; report that history/conflicts are excluded from that export. Ordinary writers must never strip a required sync descriptor as an incidental save.

Existing exact-base Darkbox deltas MAY transport a snapshot only when the exact base package bytes are available and fully verified. They do not merge transactions and are optional optimizations. At least one complete independently usable snapshot must remain obtainable.

## 14. Receipts, retention, membership and migration

A receipt is an immutable advisory JSON record with kind darkbox-sync-receipt, protocolVersion, syncId, rootSha256, replicaId, serial and frontier. Serial is independent of transaction sequence. It means that incarnation durably applied and installed resources through the stated frontier. Only compare completely valid monotone receipts for that incarnation; inconsistent receipts are diagnostics. A receipt is not a vote, deletion authorization or a promise that the device will never restore an old backup.

Version 1 has no automatic garbage collection, tombstone pruning, actor/frontier pruning, mutable active-replica membership or distributed retirement. A closed session simply publishes no more transactions. Descriptors, receipts, segments, objects and complete snapshots remain immutable and retained. A producer deleting only its own segments would still break an offline peer, so ownership alone is insufficient.

Storage growth is an explicit tradeoff. Resources are addressed once by bytes, but concurrent identical cloud publications can leave redundant physical conflict copies, and complete snapshots contain history and resource copies. Do not promise constant storage or perfect physical deduplication. Snapshot cadence is application policy; snapshots do not make old history collectable.

The application format, profile mapping and security mode are fixed for the domain. An unsupported version stops that domain; a segment cannot migrate peers one by one. For v1, format migration or manual compaction creates a new syncId from an explicitly captured/reconciled old-domain state and requires every participating device to join the new domain. Retain an independent full old-domain backup before discarding history. Any still-offline old device remains on the old domain until explicitly reconciled; its edits are not silently imported or claimed to have migrated. This is an explicit maintenance operation, not an automatic first-version protocol feature.

## 15. Field-level wire contract

Every JSON object in v1 has exactly its listed required members plus the explicitly conditional members below; unknown members are invalid, not silently ignored. In contrast, arbitrary unrelated files in the transport folder are classified as in section 4. Every hash is 64 lowercase hex; every sync/package/device/replica ID is 32 lowercase hex. All kind values are exact case-sensitive strings. Version strings are exact supported values, never range matches.

A replica descriptor has kind=darkbox-sync-replica, protocolVersion, syncId, rootSha256, replicaId, deviceId, label. label is a display-only Unicode string, at most 1024 UTF-8 bytes. Different descriptor bytes for one replicaId are an identity conflict even if no transaction has arrived. A label change requires a new session/descriptor; there is no mutable descriptor update.

A receipt has the members in section 14. Its frontier uses the exact dependency-tip row grammar from section 6. The incarnation must have a verified descriptor. serial starts at 1 and increments for that incarnation's receipts; missing receipt serials are harmless because receipts are advisory. A higher valid receipt must causally dominate the previously accepted receipt, including exact chain compatibility.

A snapshot descriptor has kind=darkbox-sync-snapshot, protocolVersion, syncId, rootSha256, replicaId, package, frontier, stateSha256. package is {path, size, sha256}, with path exactly replicas/<replicaId>/snapshots/<sha256>.darkbox. frontier must match the enclosed checkpoint after full verification. The external descriptor's own length/hash bind its complete canonical bytes through its filename.

All operation objects have an op discriminator:
- create: {op:create, collection}. The new record ID is the operation dot; there is no caller-chosen id member.
- assign: {op:assign, record, field, present}, with value required iff present is true.
- set_add: {op:set_add, record, field, value}.
- set_remove: {op:set_remove, record, field, value, tags}, where tags is the sorted unique array of observed add-dot strings specified in section 10.
- delete: {op:delete, record}.
- place: {op:place, record, field, sequence, owner, after}. owner and after are either null or record/node dot strings respectively.
- unplace: {op:unplace, record, field}.

record is the create-dot string, and its collection is recovered from that create event. Every assign/set/place/unplace must address a mapped field of the matching kind and a record live in the author's causal state. delete can also address an already tombstoned record, yielding an additional permanent delete dot. Creates earlier in the same transaction are visible; later creates are not. An assigned record reference must name its target collection and observed create dot; a deleted target may be retained as data, with its invalid/live presentation handled by profile projection.

A transaction has one to 4096 operations, all validated as an atomic group. A failure in the last operation cannot commit the first. Same-transaction operation context includes earlier operations, so removing a tag or placing after a node created earlier in the group is valid. Blob closure includes all nested typed values, including values in operations hidden by a later delete/overwrite.

checkpoint.json has kind=darkbox-sync-checkpoint, protocolVersion, syncId, rootSha256, frontier, history, state, objects. history and state are {path, size, sha256}; their paths are fixed extension-namespace history.jsonl and state.json respectively. Each objects row is {sha256, size, path}; path is an exact common-conformant package path with complete bytes matching the logical object. The complete package includes the exact root/mapping bindings; a sealed checkpoint is verified against them before state adoption. The human-readable profile must bind the same profile identifier and formatVersion as the domain root.

state.json has kind=darkbox-sync-state, protocolVersion, syncId, rootSha256, frontier, records, nodes:
- records is sorted by parsed create-dot tuple (replicaId bytes, sequence numeric, index numeric).
- Each record is {id, collection, deletedBy, registers, sets, positions}. deletedBy contains all accepted delete dots, sorted by parsed dot.
- registers is sorted by field. Each row is {field, candidates}; candidates is sorted by parsed dot and contains every causally maximal assignment as {dot, lamport, present} plus value iff present=true.
- sets is sorted by field. Each row is {field, adds, removed}; adds contains every accepted add as {dot, value}, sorted by parsed dot; removed contains the union of removed add dots, sorted by parsed dot.
- positions is sorted by field. Each row is {field, candidates}; candidates contains every causally maximal place/unplace assignment as {dot, lamport, present} plus node iff present=true, sorted by parsed dot.
- nodes contains every place node, sorted by parsed dot. Each is {id, record, field, sequence, owner, after, lamport}. id equals the place operation dot. Node ownership and parent are immutable.
- Include all created records, including deleted ones. A field row exists iff at least one corresponding accepted operation exists, even if its current value/set is absent/empty. No derived display winner, status string, local-only value or wall-clock field is included.
- The frontier is the exact verified chain-tip array. SHA-256 of the entire canonical state.json is stateSha256. Empty arrays and null sentinels are explicit; optional defaults do not change encoding.

History contains every covered canonical transaction exactly once. Transaction lines are sorted by (replicaId, sequence numeric), which need not be causal application order. Verification builds a causal-ready queue rather than blindly applying line order. A snapshot with a hole, missing resource, wrong state cache or conflicting chain is not a complete checkpoint.

mapping.json has kind=darkbox-sync-mapping, mappingVersion=1.0.0, application, storage, collections, projection:
- application is {profile, formatVersion}, identical to the root's application object.
- storage is {mode, databasePath, reservedPrefix}; mode is single-database or journal-with-caches; databasePath is a declared package database path; reservedPrefix is _darkbox_sync_. The application profile documents those reserved tables. Cache layout is application data, not a protocol transaction participant.
- collections is sorted by name. Each is {name, table, idColumn, fields, localColumns}. Names are unique. table/idColumn are exact profile SQLite names. fields is sorted by name; localColumns is a unique exact UTF-8-byte-sorted array of column names. A SQL storage column cannot be assigned contradictory synchronized/local roles.
- A field row is {name, kind, columns, codec, valueTypes}. kind is register, set or position; columns is a unique exact UTF-8-byte-sorted array of mapped storage column names; codec is an exact profile-defined adapter identifier with essential semantics in the included profile, never executable code. valueTypes is a sorted unique array from the typed-value discriminators; it is empty for positions.
- A position field additionally has sequences, a unique ASCII-sorted array of declared sequence names, and ownerCollections, a unique ASCII-sorted array of permitted owner collection names, with allowRootOwner as an explicit boolean.
- projection is {id, version, conflictPolicy, documentationPath}; id/version identify the exact registered adapter, conflictPolicy is quarantine, documentationPath is profile/profile.md. The profile must document constraint detection, deterministic quarantine closure and how its conflict view retains complete logical records. Additional presentation fallback semantics belong to that pinned adapter, not an optional unversioned JSON snippet.

The schema validates mapping structure, while the adapter validates SQL correspondence, allowed values, unique-column rules, conflict-view semantics and application invariants. An arbitrary user-defined codec cannot be automatically executed or certified by a generic materializer.

Working/sealed extension descriptors select exactly their corresponding data member sets in section 13. All namespace paths are declared in common folders. A normal generic writer that only understands common 1.4.0 or that lacks sync writer capability refuses mutation of this required extension.


## 16. Complete canonical encoding

The RFC 8785 subset used here has no JSON numeric tokens and only ASCII object keys. Sort every object's keys by ascending ASCII bytes. Emit UTF-8 with no whitespace, BOM or final newline. Emit `null`, `true` and `false` literally. Arrays retain order. Strings escape quotation mark and reverse solidus with a preceding reverse solidus; use `\b`, `\t`, `\n`, `\f`, `\r` for those five controls and lowercase `\u00xx` for every other U+0000 through U+001F character. Other Unicode scalar values are emitted as their exact UTF-8 bytes. Do not escape solidus or normalize Unicode. Reject surrogate code points, invalid UTF-8, duplicate object keys and any input whose bytes differ from this re-encoding. User-defined map keys are entry values; their separate ordering uses exact UTF-8 bytes.

JSONL history is the sole newline-framed exception: each independently canonical transaction is followed by one LF; empty history is zero bytes. There are no blank transaction lines. All integer bounds and semantic conditions remain additional to JSON Schema validation.

## 17. Working storage and profile verification

A working sync descriptor is local runtime metadata, never a conforming portable sealed checkpoint. Generic verification and creation return NotQuiescent/unsupported for that mode and never replay or modify a packaged working journal. The application reads its journal while owning the live-directory guard and writes a fresh sealed checkpoint. A new immutable checkpoint does not overwrite an earlier checkpoint.

The single authoritative SQLite journal uses `_darkbox_sync_meta`, `_darkbox_sync_history`, `_darkbox_sync_pending`, `_darkbox_sync_outbox` and `_darkbox_sync_forks`. Root bytes pin the domain; history and outgoing rows store exact canonical transaction bytes keyed by replica and decimal-string sequence. Pending rows preserve received bytes before causal/resource readiness. Outbox rows additionally store local-publication status, which does not certify cloud upload. Fork evidence is retained and blocks ordinary writes. Restored installations start new incarnations and may only republish exact old committed bytes. These tables are documented in the integrating profile alongside its synchronized and local-only columns.

The generic verifier checks canonical checkpoint resources, full causal replay, logical state equality and complete historical resource closure. It explicitly leaves application database projection unchecked unless the application registers a corresponding profile validator. A writable adapter must verify the pinned mapping/version and atomically materialize core state and its deterministic conflict view. It must not reject concurrent business conflicts merely because a naive SQL write violates a unique or foreign-key constraint.

## References

RFC 8785 is an informative reference for the fully specified encoding subset above: https://www.rfc-editor.org/rfc/rfc8785.html. The essential decoding, causality and merge rules are included here and require no network access. SHA-256 is used for content integrity, not author authentication.

## Working journal schema

The local journal schema version `1.0.0` uses these application-reserved tables.
All identity/counter strings retain their exact protocol encodings.

| Table | Columns and keys | Meaning |
| --- | --- | --- |
| `_darkbox_sync_meta` | `key TEXT PRIMARY KEY`, `value BLOB NOT NULL` | Exact root bytes, local incarnation descriptors, receipts and implementation cache hints |
| `_darkbox_sync_history` | `replica TEXT`, `sequence TEXT`, `bytes BLOB`, primary key `(replica, sequence)`, all NOT NULL | Accepted canonical transaction bytes |
| `_darkbox_sync_pending` | Same columns/key as history | Complete received bytes awaiting application |
| `_darkbox_sync_outbox` | Same columns/key as history, plus `published INTEGER NOT NULL DEFAULT 0` | Committed local bytes and local-publication status |
| `_darkbox_sync_forks` | `hash TEXT PRIMARY KEY`, `bytes BLOB NOT NULL` | Retained conflicting canonical bytes, keyed by SHA-256 |

The Rust SDK uses WITHOUT ROWID tables. Metadata key `root` stores canonical
DomainRoot JSON, `replica:<replicaId>` stores a canonical replica descriptor, and
`receipt:<replicaId>:<serial>` stores a canonical receipt. `forked` marks an unsafe
domain; it never authorizes selecting or deleting a branch. `state` is a rebuildable
canonical state cache. `cache_revision` is an implementation-local decimal-string
revision used to invalidate in-memory caches after durable commits; it is not an
operation ID or replicated clock. `receipt_serial:<replicaId>` allocates that
incarnation's advisory receipt sequence. History and its verified root remain
authoritative; no cache entry can replace independent checkpoint replay.

Resource bytes are verified before acquiring the SQLite application write barrier.
Writers recheck the causal revision and retained resource identities before the
atomic commit. The application MUST retain those objects unchanged, as with the
common retained hot-capture contract. Synchronous FULL or EXTRA and persistent
journaling are required for the SDK's durable local-commit contract.
